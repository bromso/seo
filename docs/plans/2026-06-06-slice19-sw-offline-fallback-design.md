# Slice 19 — SW Offline Fallback Page (Design)

**Date:** 2026-06-06
**Branch (when implementing):** `feat/sw-offline-fallback-slice19`
**Carry-forward from:** Slice 18 (queue TTL closed); offline UX gap: navigating to an uncached URL while offline shows a generic browser error.

---

## Goal

When the user navigates offline to a URL the browser has never visited (no cached entry), the SW serves the precached `/offline` page instead of a generic browser error. Closes the last remaining "blank page" UX gap in the offline story.

---

## Non-Goals

- No rewrite of the existing `/offline` page (it's functional).
- No "last cached: X ago" suffix on the offline page (that's the OfflineBanner's job for cached pages).
- No special handling for API or RSC payload requests — they still go through their existing strategies.
- No dashboard overlay for offline state (slice 15/16's banner already handles that case).
- No client-side router push to `/offline` on fetch error (defer to slice 20+ if needed).
- No new dependencies, no DB migration.

---

## Architecture

Add `fallbacks: { entries: [...] }` to the `Serwist` constructor in `apps/app/src/app/sw.ts`. The fallback entry targets navigation requests (`request.destination === "document"`) and serves `/offline` whenever the navigation runtime handler (the slice-7 `NetworkFirst` for `request.mode === "navigate"`) errors out — typically because the network is dead AND the requested URL has no cached entry.

Serwist precaches `/offline` automatically: the page is statically generated by Next.js and lands in `__SW_MANIFEST`. The fallback plugin returns the cached response when the runtime handler throws.

---

## The SW change

Full updated section of `apps/app/src/app/sw.ts`:

```ts
const serwist = new Serwist({
  precacheEntries: self.__SW_MANIFEST,
  skipWaiting: true,
  clientsClaim: true,
  navigationPreload: true,
  runtimeCaching: [
    /* existing strategies — unchanged */
  ],
  fallbacks: {
    entries: [
      {
        url: "/offline",
        matcher: ({ request }) => request.destination === "document",
      },
    ],
  },
})
```

The rest of `sw.ts` is unchanged — the slice-17 `sync` event listener for `audit-run-queue`, the slice-7 runtime caching strategies, all stay put.

## URL bar behavior

When the SW serves the fallback for `/dashboard/runs/abc`, the address bar stays at `/dashboard/runs/abc` while the content is the `/offline` page. This is the standard Serwist fallback pattern.

- The user sees "You're offline" content under the original URL.
- "Try Again" reloads the same URL — if network returns, they land on the real page; if not, they see the offline page again.
- No client-side redirect; no `useRouter` involvement.

If user testing reveals the URL/content mismatch is confusing, slice 20 can add a client-side `router.replace("/offline")` from a top-level error boundary. Out of scope here.

---

## Why navigation only

The matcher `({ request }) => request.destination === "document"` limits the fallback to top-level navigations. Other request types fall through to their existing handlers:

| Destination | Slice-7 handler | Slice-19 fallback applies? |
|---|---|---|
| `document` (page navigation) | `NetworkFirst` (3s timeout) → cache → ... | **Yes** — returns `/offline` |
| `script`, `style`, `font` | `CacheFirst` | No — assets already cached or fail loudly |
| `image` | `StaleWhileRevalidate` | No — broken images stay broken |
| Empty string (RSC payload, fetch) | `NetworkOnly` (for `/api/`) or default | No — handlers return their own errors |

This boundary is intentional: serving the `/offline` HTML for an RSC payload request would corrupt the dashboard's React tree.

## Smoke test (manual, post-implementation)

1. Production build + serve:
   ```bash
   bun --filter @repo/app build
   bun --filter @repo/app start
   ```
   (Serwist is disabled in dev — must use production mode.)
2. Open `app.localhost:3001`, sign in, visit `/dashboard` once so the page caches.
3. DevTools → Application → Service Workers → confirm `sw.js` is active.
4. DevTools → Application → Cache Storage → expand `serwist-precache-v2-...`; confirm `/offline` is present.
5. DevTools → Network → throttle to **Offline**.
6. Visit a never-visited URL like `/dashboard/runs/nonexistent-id` — should show the `/offline` page ("You're offline") instead of Chrome's default offline page.
7. Throttle back to **Online** → click "Try Again" → page reloads, real content (or 404) loads.
8. Visit `/dashboard` while still offline — previously-cached dashboard loads (NetworkFirst's cache fallback fires, fallback handler is NOT triggered). This confirms the fallback only fires for cache misses.
